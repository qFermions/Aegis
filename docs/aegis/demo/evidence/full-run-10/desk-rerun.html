## Fix

**What's wrong:** A staff member wants access to the billing mailbox "same as [FIRST_NAME]". Nothing is broken. This is an access request for a finance mailbox, and it needs sign-off.

**Do this:**
1. Call the requester back on the number in the firm's staff list to confirm they really sent this.
2. Exchange admin center → Recipients → Mailboxes → billing mailbox → **Mailbox delegation**. Copy the three lists into the ticket and note which rights [FIRST_NAME] has.
3. Ask the managing partner which right this person needs and get their written approval. Reading the mailbox is the usual need. Sending as the billing mailbox is a separate approval.
4. If approved: **Read and manage (Full Access)** → Edit → Add members → requester → Save → Confirm.

**Done when:** The billing mailbox shows up in their Outlook, and Aegis's check shows them on the billing mailbox's Full Access list.

**Stop if:** The callback doesn't match, or the managing partner doesn't recognise the request.

**Tell the user now:** We've got your request. We'll call you to confirm it's you, and the managing partner will need to approve it.

**Tell the user when done:** You can now open the billing inbox. It will appear in Outlook under your own mailbox. Restart Outlook if it isn't there yet.

## Details

- **Setup used:** the Customer E profile (cloud-only Microsoft 365, one office). There is no on-prem AD, so no sync step.
- **Why there's a gate:** Full Access lets the person read every message in the mailbox, past and present. At an accounting firm the billing mailbox holds client financial data, and anything they read can't be taken back (R2). "Same as [FIRST_NAME]" is not an approval. Grant only the rights the managing partner approves, even if [FIRST_NAME] has more.
- **Least privilege:** Start with Full Access only. Send As (mail goes out from the billing address) needs its own approval and its own change. Send on Behalf has no gated procedure in the runbook. If several staff end up needing this mailbox, give access to a mail-enabled security group instead. That is a separate reviewed change.
- **Temporary access:** If this is cover for leave, put the end date in the ticket. The grant doesn't expire by itself, so remove it on that date.
- **Undo:** Remove the person from Full Access on the same Mailbox delegation page.

## Fix

**What's wrong:** Okta Verify on the Mac keeps sending the user back to sign in. This started after a macOS update, and reinstalling Okta Verify didn't fix it, so the likely cause is old sign-in data left on the Mac or in Okta.

**Do this:**
1. Check first, without changing anything: in Okta Admin → Directory → People → `[UPN]`, confirm the status is **Active**. Then read Reports → System Log for sign-ins or pushes the user didn't make.
2. Ask the user to fully quit Okta Verify, open it again and sign in once.
3. Ask the user to restart the Mac and sign in once more. Write the macOS version and the Okta Verify version in the ticket.
4. If it still loops, confirm the user's identity (video call, and the manager confirms in the IT channel). Then **Clear User Sessions** (R1, see gate).

**Done when:** the user finishes one full sign-in and the System Log shows it.

**Stop if:** the System Log shows sign-ins or pushes the user didn't make. Send it to security before changing anything.

**Tell the user now:** "We're looking at it. Please fully quit Okta Verify and sign in again."

**Tell the user when done:** "You're signed in again. If it loops again, reply to this ticket."

## Details

- **Runbook:** `/okta-mfa-reset`, section "Okta Verify sign-in loop after a macOS update". The owner tested this procedure on a real ticket, but Okta's public help pages don't cover it.
- **Session clear:** Okta Admin → People → `[UPN]` → More Actions → Clear User Sessions → Clear and revoke. Write the current UTC time in the ticket as `[NOT_BEFORE]` just before you click. Nothing needs undoing: the user simply signs in again.
- **Gotcha:** Clear User Sessions only appears for active users. It doesn't appear when you open your own profile.
- **Last resort:** if the loop continues after the session clear, the next step is resetting only Okta Verify (gate `okta-mfa-reset-selected-portal`, R2, cannot be undone). That needs its own identity check, change record and approval from the head of engineering. It is **not** advised yet.
- **Out of scope:** Google 2-Step Verification is a separate control. Leave it alone.
