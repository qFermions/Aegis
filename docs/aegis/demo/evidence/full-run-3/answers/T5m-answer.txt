## Details

**Verdict:** Six messages from one sender all going missing points to filtering, not a mail outage. Invoice emails with attachments or payment links often get flagged as phish.

**What to check first**
- **Quarantine** (step 1). If the invoices are there, the reason held decides what happens next:
  - Spam or bulk: release after you confirm with the recipient.
  - High-confidence spam: review the headers first.
  - Phish or high-confidence phish: do not release.
  - Malware: can't be released.
- **Message trace** (step 2):
  - "Delivered": the mail reached the mailbox. Check the Junk folder and the mailbox's inbox rules. A rule that quietly moves or deletes vendor invoices is a classic sign of a compromised mailbox. Send that to `/security-alert-triage`, not this fix.
  - "FilteredAsSpam": the filter caught it. Go back to quarantine.
  - "Failed": the sending side or a mail-routing problem. Ask the vendor for the bounce message they got.
  - No trace at all: the mail never reached Customer C. The vendor should check which address they sent to.

**Customer C notes**
- ⚠️ **No identity-check process:** the profile has no way to verify who is asking ([org gap]). Before releasing anything, have the IT lead confirm the requester and the recipient mailbox another way, such as a callback to a known number.
- **Who approves:** the IT lead approves each release.
- **Not advised: an allow entry for the vendor.** If this keeps happening, an entry with an expiry date goes through `/email-whitelist` as its own change. Because it changes mail flow, it needs both the IT lead and the operations manager.

**⚠️ Risk:** A released message can't be pulled back. Releasing a real phish puts working links and attachments in the inbox. Release each message to one recipient only, never to all.

**Verification checklist**
- [ ] Message trace run for [SENDER], from last Tuesday to today
- [ ] Each quarantined invoice's reason reviewed
- [ ] Requester confirmed by the IT lead (identity-check gap noted)
