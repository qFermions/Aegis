## Fix
**What's wrong:** Someone may have signed in to [FIRST_NAME]'s Okta account from Romania without their knowledge.
**Do this:**
1. Okta Admin Console → Reports → System Log → search [UPN] → read the Romania events. A failed sign-in means the password may be known but the attacker was stopped. A successful sign-in or an approved Okta Verify push means the account is compromised. No Romania event at all means the email itself may be phishing.
2. Ask [FIRST_NAME] whether they approved any Okta Verify prompt they didn't start.
3. If the log shows a successful sign-in, end all of their Okta sessions: Directory → People → [UPN] → More Actions → Clear User Sessions, with tokens included.
**Done when:** the System Log shows their sessions were cleared. Aegis then checks for the session-clear event.
**Stop if:** other users show sign-ins from Romania too. That's an org-wide incident.
**Tell the user now:** Thanks for reporting this. Don't click any links in that email. IT is checking your account's sign-in history now.
**Tell the user when done:** Your account's sessions have been ended. Please sign in again and approve only prompts you start yourself.

This may need a longer plan across Okta, Google and GitHub: see Details.

## Details
**No runbook covers an Okta suspicious sign-in.** `/security-alert-triage` only covers Microsoft. These steps come from reasoning, built on `/okta-user-lifecycle` Phases A, C and D.

**Verdict:** possible account compromise. Contain first if the log confirms it. Security reports are handled at any hour under this customer's profile.

**What to check first (read-only)**
- System Log for [UPN]: country, IP, and success or failure on the sign-in. Also check MFA events: a burst of pushes points to push fatigue, and an approved push means the attacker got in.
- Status and Applications tab: which apps a session could have reached (Google, GitHub, Linear, Slack).
- Google Admin → the user's account: do they hold a super admin role? Super admins can skip Okta sign-in.

**Next steps, if the sessions are cleared but the risk stays**
- Clearing Okta sessions doesn't end sessions already open inside Google, GitHub or Slack. If the log shows those apps were reached, sign the user out of each app as its own follow-up.
- Step 4, only if a successful sign-in is confirmed and the password is likely known: gate `okta-user-lifecycle-reset-password-portal` (R2, approval from the head of engineering). Verify identity first by video call, with the manager confirming in the IT channel. Hand the temporary password over outside the ticket.
- Step 5, only if activity continues after steps 3 and 4: gate `okta-user-lifecycle-suspend-portal` (R2, reversible).
- Don't reset MFA on a possibly compromised account. A reset lets the attacker enroll their own factor (`/okta-mfa-reset`).

**Risk:** clearing sessions only signs the user out, so nothing needs undoing. Keep a copy of the System Log events before acting, as evidence.
