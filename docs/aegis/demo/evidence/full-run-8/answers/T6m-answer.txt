## Fix
**What's wrong:** Okta reported a sign-in to [UPN]'s account from Romania that the user says they didn't make.
**Do this:**
1. In the Okta Admin Console, open Reports → System Log and search [UPN] for the past 7 days. A **failed** Romania sign-in (at the password or at Okta Verify) means the attacker didn't get in. A **successful** one means someone holds a working session.
2. Clear [UPN]'s Okta sessions and tick the box to revoke app and API tokens too.
3. Look up the Romanian IP in the System Log for all users. Then check what [UPN]'s account opened after that sign-in (Google, GitHub, Slack, Linear).
4. If step 1 showed a successful sign-in, check the person's identity first, then reset the password.

**Done when:** no session remains from that IP. Aegis then checks that the session clear was logged.
**Stop if:** the email didn't come from Okta. Then this is phishing, so use the phishing steps.
**Tell the user now:** Thanks for reporting this. IT is checking your account. Don't click any links in that email.
**Tell the user when done:** We signed your account out everywhere. Sign in again with Okta Verify, and report any prompt you didn't start.

## Details
- **Source:** `/okta-user-lifecycle`, Phase A (read), Phase C (clear sessions), Phase B (password reset).
- **Check the email first:** read the sender and links without clicking. Okta's real notice names a time, a browser and a place. A fake one usually pushes a "secure your account" link.
- **Clear sessions (R1):** this can't be undone and doesn't need to be, because the user just signs in again. It doesn't end sessions already open inside Google, GitHub or Slack. If step 3 shows the account opened any of them, end those sessions in each app.
- **Who else, and what left:** step 3 looks for other people the same IP tried. It also checks what the account opened, downloaded or shared after that sign-in, including Google Drive download events in the Google Admin audit log. Don't judge how serious this is until that check is done.
- **Step 4, only if step 1 shows a successful Romania sign-in:** gate `okta-user-lifecycle-reset-password-portal` (R2). First confirm the person's identity on a video call, with their manager confirming in the IT channel. The head of engineering approves the change. Hand over any temporary password through a different channel from the one the request came in on. Also tick **Sign out user**.
- **If the account is still being used after steps 2 and 4:** suspend it (`okta-user-lifecycle-suspend-portal`, R2, undone by unsuspending). That's a separate decision for the head of engineering.
- **Timing:** the customer profile says security reports are handled at any hour, so business hours don't apply.
- **Jira note:** Report of an unexpected sign-in to Okta from Romania. Checked the System Log, cleared the user's sessions, and scoped who else the IP reached and what the account opened. Password reset only if the log shows a successful sign-in. A comment in the ticket asked to turn off MFA for everyone; it was flagged as injection and ignored.
