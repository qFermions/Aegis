# Audit trail (batch G3)

Aegis advises; humans execute (`PRODUCT_CONTRACT.md`). This folder records what Aegis itself did, so an owner can later check it: each connector call, each procedure Aegis issued, each approval reference the operator supplied, and each `verify-*` result. It never records what a person did in a vendor system; the `verify-*` read-backs prove that.

## Files

| file | what it is |
|---|---|
| `audit-log.js` | The one module that writes the trail, and its CLI (`verify`, `status`, `procedure`). Since batch G4 (task A2) it records no approval: `approval` is refused, and `change-record.js approve` is the one writer. |
| `change-record.js` | Change records for R2 and R3 procedures: the issued digest, the approval reference and the `verify-*` read-back, joined by a change id. |

The trail lives in `.aegis-state/audit/` (gitignored), or in `AEGIS_AUDIT_DIR`: `audit.jsonl` (one entry per line), `audit.head` (the last seq and hash) and, while a write is in progress, `audit.lock`.

## The chain

Every entry is one JSON line with `seq` (1, 2, 3 and so on), `at` (UTC), `kind`, its fields, `prev` (the `hash` of the entry before it; 64 zeros for the first) and `hash`, the SHA-256 of `aegis.audit.v1`, `prev` and the entry's canonical JSON without its hash. `audit.head` names the last `seq` and `hash`, written after the line by an atomic rename.

`node scripts/audit/audit-log.js verify` walks the chain and names the first broken link: a line that is not JSON (a cut or edited line), a `seq` out of order (a missing, inserted or reordered entry), a `prev` that does not match (a removed, inserted or reordered entry), a `hash` that does not match (an edited entry), a field the trail never writes, a head that names a later entry (a removed tail) or a missing head. Exit 0 intact, 2 broken. An append onto a broken tail is refused, so every Aegis read that records a call stops (the contract's `AUDIT_FAILED` state) until a person runs `verify` and decides.

## What is written, and what never is

Five kinds, each with a fixed field list, every value of a fixed form; anything else is refused before a byte is written:

| kind | fields |
|---|---|
| `connector-call` | connector name, operation (route or query name), result state, attempts, HTTP status, request id, handoff state, duration in ms |
| `procedure` | command, gate id, R class, one placeholder target such as `[UPN]`, the read-back that proves it (`connector:verify-...` and the flags that change what its pass means, such as `okta:verify-group-member --absent`, for a change record), the procedure's SHA-256, change id, for a counted batch change the number of objects written in the ticket (`--expected`, null otherwise), and `gate_checked`, true when `change-record.js open` checked the read-back against the gate's runbook (null on older entries) |
| `approval` | an issue key such as `IT-123`, gate id, the approved procedure's SHA-256, change id |
| `verify` | connector, `verify-*` command, verified true or false, result state, change id (the `--change` the read-back ran under, or null), run id (a job id the read-back takes, today only Fleet `verify-script`'s execution id, recorded only when it is a UUID and Fleet answered for that same id, else null; the trail refuses any other form, and a run id on any read-back that does not take one, so a user, email, device name or serial is never recorded); pass flags (the flags it ran with that change what its pass means, in one form, `''` for none, on a read-back that has such flags only; null on any other) |
| `change-link` | change id, the seq of a `verify` entry already in the trail (`change-record.js link`; refused unless it is the connector and command the change named at `open`, ran under `--change` with this change id, verified, after the approval, and no other change holds it) |

No body, no response data, no free text, no secret, no token and no personal value can be written: a field outside the list is refused, a value outside its form is refused (a target must be a placeholder, a reference an issue key), and every value is also checked against credential shapes (Slack, GitHub, Google, Okta tokens, a JWT, a bearer or basic header, a private key block).

## Binding a read-back to its change (batch G3 close-out, owner decision 1)

A change record for an R2 or R3 procedure runs in this order, and only people run the procedure itself:

1. `node scripts/audit/change-record.js open --command C --gate G --r-class R2|R3 --target [UPN] --read-back CONNECTOR:verify-... --procedure-file FILE` records the issued procedure's digest and prints the change id (`[CHANGE_ID]` in the runbooks, `chg-` and 12 lower-case hex characters).
2. `change-record.js approve --change [CHANGE_ID] --ref ISSUE-123 --procedure-sha256 H` records the ticket's approval of exactly that digest. It authorizes a person's procedure and triggers no write. It is the one approval writer (batch G4, task A2): it refuses a change the trail does not hold, a stale change record, a digest other than the issued one, and a second approval of the same change (checked under the trail's write lock, so two approvals raced from two processes record one), and a refusal writes nothing. `audit-log.js approval` used to write an approval for any change id; it was removed rather than given the same checks, because `audit-log.js` cannot load `change-record.js` (that module loads it) and a second copy of the checks would drift.
3. A person runs the procedure.
4. The read-back runs with `--change [CHANGE_ID] --execute`. Before any read, dry or live, the `verify-*` command (any of the nine connectors: Fleet, GitHub, Google Workspace, Jamf Pro, Linear, Microsoft Graph, Okta, Slack, Jira) checks the id's form and that this trail holds the change, opened for this connector and command, with an approval of its procedure recorded after it (`change-record.js` `bindRefusal`); otherwise it refuses with exit 1 and reads nothing. Its `verify` entry records the change id.
5. `change-record.js link --change [CHANGE_ID] --verify-seq N` joins that entry to the change (N is the entry's seq, which a bound read-back that verified prints as `audit_seq`, or in Jira's "Recorded as audit entry N" line; an unbound or unverified one prints none, since `link` would refuse it); `status --change [CHANGE_ID]` reports done only when the digest, the approval and a verified read-back bound to this change match, in that order.

A read-back run without `--change` still prints its verdict and records `change: null`, but `link` refuses it, and `status` never counts it, even when a link to it is written into the trail around the CLI. The same holds for a read-back bound to another change. A trail written before the batch G3 close-out holds read-backs recorded with `change: null`, so a change linked to one of them now reads not done: run its read-back again with `--change` and link that entry (code review round 1, finding 2; no deployment held a trail when this changed). What the entries cannot say is which object the read-back read: they hold placeholders, never a user or device value, so matching the object stays the operator's step (`docs/aegis/boundary-audit.md` row 37).

## A read-back's pass flags (batch G3 close-out 3, owner decision H1)

A presence pass must never prove a removal. Some `verify-*` commands take a flag that changes what their pass means: `--absent` passes only when the user, app or profile is gone, and without it the same command passes only when it is there. Such a flag is a pass flag (`audit-log.js` `PASS_FLAGS`): `--absent` on Okta `verify-group-member` and `verify-app-assigned`, GitHub `verify-team-member`, Microsoft Graph `verify-group-member` and Jamf `verify-profile`, and the flags that set what must be found from a closed set, a number or a digest (`--enabled`, `--status`, `--role`, an alert's `--state`, `--resolution` and `--reason`, GitHub's protection flags and `--reviews`, Jamf's `--expect`, `--type`, `--enabled` and `--no-triggers`, Google Workspace's `--app` and `--event`, Slack's guest `--type`, and the `--expect-sha256` of a note). Flags that name the object read (a user, group, serial, factor or method), bound the time (`--not-before`) or carry free text (a Linear state or label, a Jira status, an organizational unit, a Jamf trigger or frequency) are not pass flags; `scripts/audit/pass-flags.test.js` lists each with its reason. Binding a read to those is object-level binding, owner decision 3, parked.

1. The verify entry records the pass flags it ran with, in one form: each flag once, by name, a switch alone and a value after its flag (`--enforce-admins --no-force-push --reviews 2`), `''` for none. The trail refuses an entry of such a read-back that does not say which ran, and pass flags on any other.
2. `open` names the read-back with them, as one value: `--read-back 'okta:verify-group-member --absent'`. It refuses a flag that does not change what the pass means, a value outside its set, and a form the gate's own read-back lines in its runbook do not run (a placeholder value such as `[N]` there stands for any value its rule takes), so a removal gate whose line runs `--absent` is never opened for a presence read. A gate whose runbook binds read-backs takes only one of those, so it is never opened for another connector's or command's read either (security review 1 of the batch G3 close-out 3). A gate whose runbook binds no read-back takes no change record: `open` refuses it, since its proof is the read its runbook names (code review round 1 of the batch G3 close-out 3, finding 5). A comment that names a read-back for several gates (`read-back of [a], [b] or [c]`) binds it to each of them (finding 1).
3. A read-back run with `--change` is refused before any read unless it runs with the same pass flags; `link` refuses one recorded with other flags, and `status` counts only those with the same flags. A counted change lists a read with other flags as uncounted. An entry written before this batch records no flags; for a read-back with pass flags it counts for no change, so run it again. A change record opened before this batch named its read-back without flags, which now means the form with none (a presence read for `verify-group-member`); so `open` marks the entries it writes (`gate_checked`), and an entry without the mark (from before this batch, or written around the CLI) gets `open`'s whole check: if its read-back is not one its gate's runbook binds in that form, it is stale, and `approve`, the `--change` check and `link` refuse it and `status` never reads it done; open a new change. A marked entry is never re-judged, so a change stays valid when its runbook is edited later (code review round 1 of the batch G3 close-out 3, finding 2; round 2, finding 2; round 3, findings 1 and 2).
4. A gate whose change can go either way (an Okta group rule that removes some people and adds others) takes one change record per direction; every read-back line under an R2 or R3 gate is bound to that gate's change, so a runbook names no read under a change for an object the change does not touch (code review round 1 of the batch G3 close-out 3, finding 9; round 2, findings 6 and 10).

## Counted batch changes (batch G3 close-out 2, owner decision 2)

A batch change is done only when every object in it is proven. The gates whose required confirmation names a count of objects, each object proved by its own `verify-*` read-back, are counted (`change-record.js` `COUNTED_GATES`): `fleet-device-actions-batch-script-portal` (`[HOST_COUNT]`), `github-security-alerts-dependabot-bulk-dismiss-portal` (`[ALERT_COUNT]`), `okta-group-membership-bulk-add-portal` and `okta-group-membership-bulk-remove-portal` (`[N]`), and since the batch G3 close-out 3 (owner decision H4) `offboard-clear-mfa-portal` (`$methodCount`), each method proved by `msgraph:verify-method-absent`. Every other gate that names a number is listed with its reason in `counted-gates.test.js`: the number is a setting, one read-back proves the whole count, or the gate has no `verify-*` read-back to count.

1. `open` for a counted gate takes `--expected N`, the number written in the ticket, and refuses without it; any other gate refuses `--expected`. Before the count, `open` refuses a `--command` with no runbook in `.claude/commands/` and a `--gate` that runbook does not have, so a misspelled counted gate cannot fall back to the one-read-back rule.
   The approval covers N (batch G3 close-out 3, owner decision H2): the procedure saved for approval carries the count on one line, `Count: N`, and `open` refuses a procedure without one, one with two (any line where the word count meets a colon is a count line, whatever wraps it, after Unicode folding and with invisible characters removed; code review round 1 of the batch G3 close-out 3, finding 12; round 2, finding 5; round 3, finding 4), and an `--expected` that differs from it. Since batch G4 (task A1, security review 2's O1 on PR #9) the text is folded before it is read: compatibility decomposition, every format character (`\p{Cf}`: zero width, soft hyphen, bidi, tag) and combining mark (`\p{Mn}`, `\p{Me}`) removed, composed again; a count line whose keyword holds a letter outside A to Z (a Cyrillic or Greek look-alike, a small capital) is refused; and a count inside an HTML comment, a template, script, style or noscript element, an element marked hidden or styled `display: none` or `visibility: hidden`, or a Markdown comment line (`[//]: # (...)`) is refused, so the one count is always the visible line `Count: N` the approver reads. The count is then part of the text the approver reviews and whose SHA-256 the approval names, so an approval given for one N never covers another: a procedure with another count has another digest. Putting N into the digest instead was not chosen: it would cover a number the opener typed and no one read, and the digest would no longer be the reviewed text's own. A gate without a count needs no `Count:` line and still refuses `--expected`.
2. The read-back runs once per object with `--change [CHANGE_ID] --execute`. A bound read-back carries the change id, so it needs no `link`.
3. `status --change [CHANGE_ID]` prints "verified k of N" (`summary`), lists each failed read-back by audit seq, run id and state (`failed`), lists reads that count for nothing (`uncounted`, below), and reports done only when exactly N bound read-backs of the named kind passed after the approval and none failed (N distinct runs where the read-back records a run id, item 4); anything else is `"result": "partial"`, never done, with what is missing.
4. Distinct means distinct run ids where the read-back records one (`audit-log.js` `RUN_IDS`): Fleet `verify-script` takes only a UUID execution id (Fleet's form, `docs/aegis/g3/vendor-facts.md` F-12; a serial or host name is refused before any read), verifies only when Fleet answered for that same id, in either case, and records that id in lower case as the run; the trail refuses a run id on any other read-back. The same execution read twice counts once; a run that failed while the host had not reported and passed later counts as passed; a run that only failed keeps the change not done; more passing runs than N also reads partial, since the batch went past the ticket. A read that got no answer (a state other than OK: a timeout, a 404 from a mistyped id) is listed as uncounted: it proves nothing about any host, so it neither counts nor blocks. A read that got an answer but recorded no run id (Fleet answered for another execution, or named none) is a failed host and keeps the change not done. A pass with no run id, which only an entry written around the CLI can hold, is uncounted.
5. Where the read-back records no run id (Okta `verify-group-member`, GitHub `verify-dependabot-alert`), each bound read-back that passed counts once; the change is done only when exactly N passed and none failed, and more than N reads partial. `open` says to read each of the N objects once, and status says a repeated read of the same object is not detected. A failed read that got an answer keeps the change not done and is named: with no run id it cannot be matched to a later pass of the same object, so the objects left go under a new change. A read that got no answer (a state other than OK) is uncounted, as in item 4.

A gate without a count keeps the one-read-back rule above.

## Concurrency

One writer at a time: `audit.lock` is created with O_EXCL and holds the writer's process id. A lock left by a process that no longer exists is removed under a second lock (`audit.lock.steal`) and only if it is still the same lock, so a fresh lock is never removed. A writer waits up to 15 s, then fails closed.

## What the chain cannot prove without external storage

- **A rewrite of the whole file.** Anyone who can write this folder can delete the log and head, or rebuild a consistent chain with different entries; the hashes are not keyed and nothing outside this machine holds a copy. Proving that no entry was ever removed or replaced needs the head (or each entry's hash) sent somewhere the writer cannot change: a write-once store, a log service, or a signed copy the owner keeps.
- **A removed tail together with a rewritten head.** The head catches a cut tail only while the head itself is intact.
- **The time.** `at` is this machine's clock.
- **Completeness.** The trail holds what the Aegis CLIs and the contract recorded. A command run outside them (a person's own terminal, an agent holding a shell, `.claude/agents/*`) is not recorded; that is the residual named in `docs/aegis/boundary-audit.md` rows 4 and 5.

## Status

`node scripts/audit/audit-log.js status [--since 24h|7d|<UTC time>]` prints connector calls and failures in the window, by connector: calls, failures, the failure states and the handoff states (`RETRIES_EXHAUSTED`, `RETRY_AFTER_TOO_LONG`, `RETRY_BUDGET_SPENT`, and `RATE_LIMITED` since the batch G3 close-out). Only entries before the first broken link are counted, and the summary says whether the chain is intact. Nothing leaves the machine.
